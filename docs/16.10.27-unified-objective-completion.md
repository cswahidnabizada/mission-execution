# 16.10.27 Unified Objective Completion System

## User-visible loop
1. The Super Admin states an objective and confirms success criteria, scope and constraints.
2. The orchestrator reads canonical context and lists what is verified, missing, blocked or unknown.
3. The system asks for only the next missing input, with bounded validation.
4. Submitted values become objective context/proposals; they are not authority to create or publish canonical records.
5. The system reassesses and chooses one eligible step through existing capability and authorization paths.
6. The effect is reconciled against trusted evidence. Failure or uncertainty creates recovery work rather than a blind retry.
7. The loop continues until verified completion is supported by a separate trusted completion gate, or remains waiting/blocked/escalated.

## Completion gate and honest boundary

A separate completion endpoint now requires explicit Super Admin step-up authorization, a fresh completion candidate, non-stale outcome evidence, VERIFIED status for every success criterion and evidence requirement, no unresolved recovery, fresh canonical context with no unavailable authorities, and all persisted steps completed. It records completion in the objective/run, event history and audit trail using revision-checked writes. The gate does not create verification evidence or infer the meaning of arbitrary prose. Trusted domain-specific verification adapters must still supply canonical evidence for criteria. No live production interaction, deployment, or successful Germany logistics mission is claimed by this package.

## Governance

Objective is a coordinator, not a new source of truth. Product and market mutations remain with Product Factory and Market Factory. Mission lifecycle, tenant authorization, resource governance, identity and billing retain their existing canonical authorities. User-provided text is data only, never executable instructions.
