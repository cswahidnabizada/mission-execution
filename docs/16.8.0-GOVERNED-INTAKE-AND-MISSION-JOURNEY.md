# ON Mission 16.8.0 — Governed Intake and Canonical Mission Journey

## Why this release exists

Data Entry, structured data imports, and Market Factory package imports now share a provenance and intake coordination layer. This layer is deliberately not a canonical business authority. It records what entered, who initiated it, the source hash, idempotency, validation outcome, scope, and canonical target while preserving the existing domain writer for each resource family.

## Intake journey

`RECEIVE → HASH → SCAN → VALIDATE → CLASSIFY → DEDUPLICATE → DEPENDENCY ANALYSIS → PREVIEW → APPROVE → COMMIT → VERIFY`

| Source | Governed path | Canonical mutation boundary |
|---|---|---|
| Manual reusable data entry | Data Entry preview → intake record → validation/dependency checks → approval/commit | Existing reusable-data or domain service |
| Structured multi-item import | One batch → per-item hash/deduplication/validation → blocked/previewed item results → explicit commit | Existing Data Entry commit path; partial results remain visible |
| Market package JSON/ZIP | Package intake → source hash → staged package version → readiness/reconciliation preview | Existing Market Factory authorized publication lifecycle only |

A preview is not a commit. A committed Data Entry record is not a published product. An imported market package is not LIVE. A market only becomes LIVE after the governed `AUTHORIZED → PUBLISHED → VERIFIED → LIVE` release flow and defaults onboarding to `INVITE_ONLY`.

## Full canonical mission journey — implementation vs proof

The following statuses distinguish code/contract presence from fresh production runtime proof. Static/SQLite tests passing do not mean a live customer mission has been certified in production.

| Journey phase | Current implementation direction | Remaining proof / action |
|---|---|---|
| OBSERVE | Canonical mission context, situation, telemetry, and operational projections exist | Re-run against the deployed runtime; verify source freshness and tenant scope |
| UNDERSTAND | Mission situation/context and intelligence engines exist | Verify one real mission’s context is complete and does not infer missing state |
| PLAN | Governed planner and plan contract exist | Live plan evaluation against current mission truth and actual resources |
| EVALUATE | Canonical plan evaluation and risk/dependency gates exist | Exercise stale context, missing capability/resource, uncertainty, and recovery cases in staging |
| ACCEPT | Explicit acceptance boundary exists | Prove unaccepted plans cannot authorize execution in the deployed runtime |
| AUTHORIZE | Canonical action/capability/resource contracts and step-up boundaries exist | Run primary-user and adversarial-user authorization tests against live runtime |
| PREPARE | Resource readiness and Market Launch Workbench exist | Clear real prerequisites; distinguish evidence accepted from checkbox completion |
| ASSIGN | Singular canonical assignment authority and subject model exist | Verify concurrency, stale assignment, unauthorized assignment, and tenant isolation live |
| EXECUTE | Governed execution coordinator/runtime exists | Complete an actual controlled mission action in a staging/customer-approved environment |
| EFFECT | Effect evidence boundary exists | Verify unknown/ambiguous effect never becomes success without authoritative evidence |
| VERIFY | Verification is separate from execution/effect | Verify outcome against independent evidence; test contradictory and missing evidence |
| RECOVER | Recovery/reconciliation paths and test harnesses exist | Execute a live failure/recovery scenario; prove no duplicate effect or stale truth override |
| OUTCOME | Outcome engine and canonical outcome records exist | Verify final outcome is tied to mission/evidence and recorded exactly once |
| LEARN | Outcome history and recalibration foundations exist | Prove only verified outcomes update learning/calibration; measure calibration before autonomy increases |
| NEXT SITUATION | Next Situation continuity engine exists | Prove unresolved missions retain a valid next action or waiting/escalation condition |
| OBSERVE loop | Closed-loop architecture is defined | Re-run the full journey from the next situation without losing canonical truth or event history |

## Permanent invariants

- One canonical truth per domain; projections and intake records never become shadow authorities.
- No cross-tenant leakage or unauthorized responsibility.
- No impossible custody or critical transition without recorded evidence.
- No state without a valid predecessor; stale actions cannot override newer truth.
- Every non-terminal mission has a valid next action, waiting condition, escalation, or breach posture.
- AI/agents may read canonical context and propose/execute only through governed actions; they cannot bypass authorization, capability/resource contracts, or evidence verification.
- Security → Truth → Liveness → Stability → Experience → Scale remains the governing priority order.
