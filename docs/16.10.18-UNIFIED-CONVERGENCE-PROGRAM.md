# Mission Execution — Unified Convergence Program

## Product invariant
One objective. One canonical truth per domain. One governed execution path. Evidence for every claimed outcome.

## Architecture layers
1. Experience: customer mission workspace, executor workspace, Super Admin Command Center.
2. Objective and intelligence: context retrieval, structured planning, dependencies, risk evaluation.
3. Canonical execution core: mission lifecycle, action registry, capability contracts, authorization, owning domain services.
4. Evidence and recovery: operation journal, evidence, effect verification, outcome, recovery, audit.
5. Platform foundation: tenant isolation, resource governance, market/product release governance, billing and observability.

The orchestrator coordinates authorities; it never becomes a competing authority for mission, product, market, resource, billing or identity truth.

## Interface model
- Command: objective intake, current situation, next safe step, approvals, exceptions.
- Build: product identity, data catalog, countries, sectors, policies and composition.
- Release & Launch: Market Factory, immutable versions, readiness, test lab, authorization, publication, verification and activation.
- Operate: missions, assignments, actions, evidence, waiting conditions, escalation and recovery.
- Govern & Recover: access, infrastructure, residency, audit, billing controls, health, backups and incident recovery.

These are navigational groupings over the existing authorities, not new applications or duplicate registries.

## State presentation contract
`READY`, `BLOCKED`, `WAITING`, `DEGRADED`, `UNKNOWN`, and `COMPLETE` must remain distinct. Empty results, unavailable authorities and real zero counts must not be conflated. Every readiness claim must be traceable to current authoritative evidence.

## Execution contract
Each adapter must be explicit and allowlisted; validate actor, tenant, capability, risk, environment and resource scope; re-read canonical truth; use idempotency and optimistic revision/lease protection; persist an operation record; verify actual effect; and define retry, reconciliation or human escalation. Unsupported operations fail closed.

## Release waves and gates
A. Inventory all active routes, services, writers, tables, migrations, UI renderers and adapters; map one authority per domain.
B. Resolve security/truth conflicts; test tenant isolation, authorization, concurrency and audit.
C. Unify interface/navigation and objective orchestration; verify resumability and evidence.
D. Certify Germany market preparation and controlled logistics mission through failure/recovery.
E. Expand autonomy only for certified adapters; verify monitoring, backup restoration and rollback.

## Permanent priorities
Security → Truth → Liveness → Stability → Experience → Scale.

## Canonical mission journey — required on every release report
OBSERVE → UNDERSTAND → PLAN → EVALUATE → ACCEPT → AUTHORIZE → PREPARE → ASSIGN → EXECUTE → EFFECT → VERIFY → RECOVER → OUTCOME → LEARN → NEXT SITUATION → OBSERVE.

For each release, report completed, remaining, blocked and evidence-unverified transitions. Never infer completion from source presence or deployment success alone.
