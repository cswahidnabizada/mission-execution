# 16.114 operational completion notes

## Qarz aging and cases
The aging API reads the existing canonical private ledger and computes outstanding balances without storing a duplicate balance authority. Case status is a workflow overlay; settlement remains owned by the existing ledger and journal. Event history is append-only. A case acknowledgement is only an internal actor action, not verified counterparty acceptance.

## Business-book period controls
Period locks are tenant scoped and immutable. The normal sync path checks the lock before constructing D1 writes. Direct journal adjustments also check the target period. There is no in-chat or UI period reopening path; reopening must be a separately reviewed release with dual control and full audit.

## Opening balances and refunds
Opening balances create balanced journal-only postings to/from opening equity. The permitted accounts are limited. Refunds create balanced sales-return postings against cash or receivables. These adjustments do not edit the original journal or operational entry. Stock returns and taxes are intentionally not inferred.

## Runtime certification boundary
The existing runtime certification harness executes against a deployed Worker and tests the canonical mission journey. It requires credentials and explicit permissions, including a second tenant for adversarial testing. No live run is claimed in this source build. Simulation Lab's synthetic scenarios still do not execute the actual production service graph; that remains an open engineering item.

## Human and market gates
No software build can manufacture legal approval, native-speaker translation validation, metrology approval, merchant acceptance, or contributor consent. These must be gathered from real reviewers and participants, stored as canonical evidence, and then evaluated by the existing market/capability gates.

## Signed staging runtime receipt
The Simulation Lab can now receive runtime-verified evidence from a protected CI runner. The runner must execute the existing canonical mission runtime harness against a non-production HTTPS Worker, using disposable test data and distinct tenant accounts. It signs the complete receipt with `SIMULATION_RUNTIME_RECEIPT_SECRET`. The Worker verifies HMAC, release identity, time window, scenario/capability/market scope, safety invariants and all canonical journey phases before writing immutable `runtime_verified` evidence. This bridge is implemented in source; it has not been exercised against a deployed staging Worker in this session.
