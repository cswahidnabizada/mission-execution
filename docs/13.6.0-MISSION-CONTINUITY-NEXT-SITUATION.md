# ON Mission 13.6.0 — Mission Continuity + Next Situation Engine

## Purpose
13.6 turns the previously bounded next-situation signal into a durable, canonical continuity projection. The objective is to make missions continuously operable without silently creating new truth, authorization, assignment or execution.

## Canonical journey
`OBSERVE → UNDERSTAND → PLAN → POLICY CHECK → AUTHORIZE → PREPARE → ASSIGN → EXECUTE → EFFECT → VERIFY → RECOVER → OUTCOME → LEARN → NEXT SITUATION`

## Architecture
- `mission-continuity-authority.service.js` is the sole continuity authority.
- `mission_next_situations` is append-only and tenant-scoped.
- Mission Truth remains authoritative for mission state and lifecycle.
- Mission Assignment remains authoritative for responsibility.
- Outcome remains authoritative for objective assessment.
- Continuity never authorizes or executes.
- Agent history consumes continuity; it does not derive a second next-situation model.

## Continuity semantics
- `ACHIEVED` → `NEXT_SITUATION_READY / OBSERVE_NEXT_SITUATION`
- unresolved recovery or critical exception → `RECOVERY_REQUIRED`
- missing assignment → `ACTIONABLE / MISSION_ASSIGNMENT`
- failed attempt → `ACTIONABLE / REPLAN_AND_REAUTHORIZE`
- partial achievement → `ACTIONABLE / PLAN_NEXT_ACTION`
- waiting → `WAITING / WAIT_FOR_PRECONDITION`
- blocked → `RECOVERY_REQUIRED / REASSESS_AND_RECOVER`
- cancellation → `TERMINAL`
- otherwise → `DEFERRED / GATHER_EVIDENCE_OR_REPLAN`

## Safety
No next-situation record can create an authorization, assignment or execution. A next situation is a governed signal for the next planning/observation cycle.

## Idempotency and concurrency
Continuity keys are deterministic from mission/outcome context. Concurrent sequence allocation is recovered by re-reading an existing continuity key or retrying against the latest sequence.

The release gate includes the dedicated 13.6 certification plus the full historical architecture/security/data/runtime/UI suite.
