## Finding fixed
Operational mission-management completion intents could resolve a `mission_management_requirements` row using only company/mission/requirement identity. Because restricted mission contexts intentionally provide read access before execution ownership is established, a caller who obtained a requirement ID could potentially cross the read/write boundary and mark another actor's operational requirement resolved.

## Canonical fix
1. `resolveRequirement()` now requires the requested actor type and actor ID to match the resolver.
2. Actor mismatch fails closed with HTTP 403 and `REQUIREMENT_ACTOR_MISMATCH`.
3. `share_current_location`, `resolve_traffic`, `resolve_waiting`, and `start_navigation` now require an authenticated assigned driver/executor actor.
4. Completion intents must provide the canonical requirement ID.
5. The requirement resolution remains behind `guardedMissionMutation()` and the mission mutation fence.
6. A permanent release gate `check-10-71-4-requirement-actor-isolation.mjs` prevents regression.

## Resulting invariant
Read access to a mission context never implies operational write authority. A requirement can only transition from `open` to `resolved` when the canonical requested actor matches the authenticated operational actor.
