# ON Mission 12.9.0 — Execution Intent Separation

## Purpose

12.9.0 advances the mission-execution journey from capability contracts to explicit execution intent. It does not create another mission-truth authority. The execution intent is an immutable execution ledger that makes the boundary between intended effect, external side effect, verification and canonical effect commit explicit.

## Permanent priorities

Security → Truth → Liveness → Stability → Experience → Scale

## Unified capability journey

OBSERVE → UNDERSTAND → PLAN → POLICY CHECK → AUTHORIZE → PREPARE → EXECUTE → VERIFY → RECOVER → OUTCOME → LEARN → NEXT SITUATION

For externally effective actions, EXECUTE is now represented as:

1. record canonical execution intent;
2. dispatch through Provider Integration;
3. capture provider operation identity;
4. verify the external effect;
5. commit the canonical effect through the existing canonical action authority;
6. record outcome;
7. recover if canonical truth cannot be reconciled with the verified external effect.

## What changed

### Execution Intent

Added `mission_execution_intents` as an execution ledger. It records intent identity, mission scope, action, request hash, state token, requested effect, execution mode, provider operation identity, canonical result, verification and recovery evidence.

The intent ledger is not mission truth and cannot replace the canonical lifecycle authority.

### Capability separation

The Execution, Provider Integration, Verification and Recovery contracts were advanced to version 2. Their contracts explicitly require intent/effect evidence and reconciliation.

### Provider boundary

Provider execution now receives the execution intent identity. The provider operation cannot be treated as the canonical mission effect merely because the provider returned success.

### Canonical effect

The existing canonical action authority remains responsible for mission mutation. It is invoked only after the external provider operation has been verified when the action requires an external effect.

### Unknown handling

Provider failures or uncertain provider states remain unresolved. They do not become success and are not automatically retried without reconciliation.

## Real-world correctness

The important invariant is now:

`INTENT_RECORDED → EXTERNAL_EFFECT → VERIFIED → CANONICAL_EFFECT`

If the provider effect is verified but canonical mutation fails, the execution becomes `RECOVERY_REQUIRED` rather than pretending the mission succeeded.

If provider state is unknown, the execution becomes `EXTERNAL_UNKNOWN` and remains unresolved until verification/reconciliation.

## Architecture

Super Admin → Resource Registry → Resource Contract → Owning Capability → Canonical Authority

Mission execution remains:

Mission Execution Coordinator → Capability Contracts → Canonical Authorities → Provider Adapters → Real World

No new mission truth store, provider authority, sector-specific execution engine or parallel lifecycle writer is introduced.
