# 16.108–16.113 — One platform, many market experiences

## Canonical architecture rule

ON Mission remains one governed platform. Identity, organization/tenant context, authorization, audit, mission lifecycle, canonical resources, data residency, privacy, provider controls and release governance remain shared authorities. Country/sector packages configure experience and capabilities; they do not own duplicate copies of those domains.

## 16.108 — Capability governance

The capability registry stores reusable capability definitions and country/sector bindings. Current definitions and bindings are source-seeded; the Super Admin UI governs their lifecycle and evidence but does not yet author new contract versions. Each binding carries version, lifecycle state, configuration, dependencies, required evidence, simulation reference and release reference. The lifecycle is:

`DEFINED → CONFIGURED → SIMULATED → CERTIFIED → PUBLISHED → ACTIVATED → MONITORED`

Suspension and retirement are controlled transitions. Publication is discovery permission; activation is permission to execute. They are deliberately separate.

Super Admin's **Capabilities & Data** workspace is an integrated control surface over the registry, Daftar market profile authority, pilot reviews, tenant allowlist and public data publication authority. It is not a replacement for Market Factory, canonical identity or domain service ownership.

## 16.109 — Shared Simulation Lab

The existing Simulation Lab hosts the scenario catalogue for Germany Logistics and Afghanistan Daftar. Scenarios are synthetic and deterministic. Each saved run is immutable and marked `client_model_unverified`. It can be linked to a capability as model-only evidence after scope checks, but the link does not advance lifecycle or certify a release.

Current model scenarios:

- Shop day: stock receipt, sale, stock balance and balanced book.
- Qarz: credit, partial settlement and remaining receivable.
- Offline replay: idempotency and duplicate prevention.
- Consent withdrawal: contributor removal and cache invalidation.
- Cohort privacy: suppress a market value below minimum cohort.
- Tenant isolation: deny cross-tenant ledger/evidence reads.
- Inactive market: block write before operational mutation.
- Germany Logistics: normal mission journey, provider unavailable, blocked route, mission recovery, device disconnect, missing proof, late delivery and cancellation through the existing canonical planning simulation model.

These models do not execute the deployed production service code. A separate isolated runtime adapter and fault-injection harness are required before claiming runtime-backed simulation certification. The API intentionally blocks SIMULATED/CERTIFIED lifecycle transitions until a server-side runtime verification receipt and immutable runtime-verified evidence link exist.

## 16.110 — Business Book

The private Daftar event and the accounting projection are linked, not conflated. Every supported financial entry creates a balanced debit/credit pair in the same D1 batch. Each journal event is single-currency and append-only. Non-cash methods use a clearing account and remain merchant-reported until an authorized provider integration confirms settlement.

Current accounts include cash, receivables, payables, inventory, sales revenue, other income, operating expense, wage expense, freight expense, sales returns, adjustment clearing and opening equity. Current v1 posting rules cover sale, purchase, expense, service, wage, freight and credit settlement. Receivable and payable settlements are separated by the original give/get direction. The UI provides merchant-printable receipts and 30-day reports. Opening balance, refunds/returns, taxes, locked periods, Qarz aging/reminders/disputes and external accounting connectors remain future extensions.

## 16.111 — PWA and portability

The installable PWA caches the shell and static Daftar assets but never caches API responses. Transaction receipts and the business-book statement use browser print-to-PDF and are explicitly not signed payment or statutory documents. Authentication must first occur online. Offline records remain encrypted in identity/tenant-scoped IndexedDB and synchronize through the existing idempotent endpoint.

CSV and JSON exports are owner/admin-only and audited. PDF is a browser print-to-PDF statement. Encrypted ZIP uses AES-256-GCM with PBKDF2-SHA-256 and includes a manifest. The restore endpoint performs a bounded, scoped validation preview only. Live restore remains disabled until conflict reconciliation, source-to-target mapping, rollback and restore acceptance tests are complete.

## 16.112 — Afghanistan pilot governance

A pilot profile is not generally open. Organizations must be allowlisted by Super Admin for the exact Afghanistan sector. Pilot reviews are append-only and require linked active evidence files. Profile activation requires the country product launch plus accepted legal, operational, merchant acceptance, security and data-residency reviews. Local unit conversions additionally require accepted metrology evidence.

Dari and Pashto translations are initial beta coverage. Native-speaker and legal review remain mandatory. A review record is evidence of a human review, not proof that the review itself was competent or legally sufficient.

## 16.113 — Public data

The public API is a read-only publication projection. Price indicators are available only after explicit contributor consent, current market activation, minimum independent cohort, outlier filtering, quality pass and freshness gates. Approved FX references come from the existing platform-approved quote authority and are labeled separately from merchant-reported prices.

Public responses contain no tenant IDs, counterparty labels, contributor keys or raw events. A missing or stale publication returns no public values; it never fabricates zero prices. API access is rate-limited and logged without storing IP addresses in the access log table.
