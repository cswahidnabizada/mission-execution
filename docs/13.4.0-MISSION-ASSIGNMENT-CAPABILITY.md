# ON Mission 13.4.0 — Mission Assignment Capability + Subject Governance

## Purpose

13.4.0 makes Mission Assignment a first-class governed PREPARE capability while preserving the existing canonical mission assignment authority.

The target journey remains:

OBSERVE → UNDERSTAND → PLAN → POLICY CHECK → AUTHORIZE → PREPARE → EXECUTE → VERIFY → RECOVER → OUTCOME → LEARN → NEXT SITUATION

The Mission Assignment Capability operates inside PREPARE. It understands current mission truth, sector/country scope, current assignment, operational candidate evidence, capabilities, constraints and availability, then produces an explainable non-authoritative decision.

## Authority model

- `mission_assignment_authority` remains the sole canonical writer of `mission_assignments`.
- The Mission Assignment Capability does not create a second assignment truth.
- `mission_assignment_subjects` is an assignment-eligibility identity projection. Operational/resource truth remains owned by the declared source authority.
- Sharing remains delegated to the existing distribution/network authority.
- Custody and responsibility transitions remain owned by the existing custody/responsibility authority.
- Mission Execution Coordinator remains the only application-level execution conductor.

## Assignment subjects

Canonical assignment rows may now represent:

- `driver`
- `executor`
- `device`
- `robot`

Devices and robots require a verified `mission_assignment_subjects` record. The record carries source authority, source identifier, capability evidence, constraints, location metadata and observation freshness. Unknown or stale availability is never automatic eligibility.

## Decision model

The capability can recommend:

- `ASSIGN`
- `REASSIGN`
- `SHARE`
- `WAIT`
- `ESCALATE`

Recommendations contain score, confidence, reasons, constraints and a context hash. They are persisted as `mission_assignment_decisions` and remain non-authoritative until an explicit governed commit.

## Safety rules

1. One active execution assignment per mission.
2. No assignment without current mission truth.
3. No robot/device assignment without verified subject identity.
4. Unknown availability is never treated as eligible.
5. Reassignment requires an explicit decision and is blocked during active physical custody unless the custody authority permits it.
6. Sharing is only suggested by Mission Assignment; the existing sharing/distribution authority performs the actual sharing operation.
7. Execution is fail-closed if assignment is absent, conflicted, or requires reassignment/sharing/escalation.
8. Assignment contracts are required before assignment reads or writes.
9. Assignment context and decision provenance remain auditable.

## Execution integration

The Mission Execution Coordinator now enforces:

PREPARE → Mission Assignment → valid execution owner → capability/resource contract → EXECUTE

A mission without a valid assignment cannot cross the execution boundary.
