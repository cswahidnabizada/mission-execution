# ON Mission 12.8.0 — Execution Integrity + Capability Contract Foundation

## Purpose

12.8.0 is the first convergence release after the 12.7.0 Resource Management foundation. Its purpose is to make capability boundaries explicit, make canonical/resource failures visible, and strengthen execution correctness without replacing existing canonical authorities.

## Permanent priorities

Security → Truth → Liveness → Stability → Experience → Scale

## Capability contract model

Every governed capability is described by purpose, inputs, outputs, commands, queries, resource types, risk class, tenant scope, side effects, dependencies, preconditions, postconditions, failure, verification, recovery, health and observability contracts.

The initial registry covers:

- Mission Intake
- Mission Truth
- Situation Intelligence
- Responsibility
- Readiness
- Planning
- Authorization
- Execution
- Provider Integration
- Verification
- Recovery
- Outcome
- Learning
- Communication
- Resource Governance
- Platform Control / Super Admin

The registry is contract metadata. It is not a second domain authority.

## Resource contract model

Super Admin remains a governance/control capability:

`Super Admin → Resource Registry → Resource Contract → Owning Capability → Canonical Authority`

Resource contracts now carry owner capability, risk, step-up requirement, identity, lifecycle, provenance, consumer scope and version metadata for the first high-risk platform resource classes.

## Correctness fixes

### Data Entry recovery

Stale-commit recovery previously requested `LIMIT 2` but consumed only `.first()`. It now reads all returned rows and distinguishes:

- 0 matches → reopen safely;
- 1 match → reconcile;
- 2 matches → `COMMIT_RECOVERY_AMBIGUOUS` / manual recovery.

### Resource dependency graph

Canonical dependency read failures are no longer swallowed. Tenant resource graphs now expose `AUTHORITY_UNAVAILABLE` and `DEGRADED` completeness so missing canonical information cannot appear as an empty dependency set.

### Governed execution

Agent execution now requires the canonical Execution Capability Contract. External-provider execution additionally requires the Provider Integration Capability Contract. Contract summaries are captured in execution-attempt metadata.

## External provider ordering — intentionally still gated

The current provider integration path can dispatch an external effect before canonical action mutation. 12.8.0 does **not** pretend that this is solved. The safe migration requires every provider action contract to distinguish:

1. canonical execution intent;
2. provider dispatch;
3. provider operation identity;
4. provider verification;
5. canonical effect commit;
6. recovery when reality and canonical truth diverge.

That work is the next execution-integrity wave and must not be bypassed.
